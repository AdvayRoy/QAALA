# QALAA — Cross-Agency Emergency Authority Gate (SYNTHETIC DEMO)

QALAA is a working prototype of an authority gate for AI actions across agencies.
Everything in it is synthetic: Entity A (requesting agency), Entity B (resource
owner), Entity C (uninvolved), Agent 47, Incident 024.

The core loop is real and server-enforced:

```
RESET → no authority → telemetry 403
→ declare Incident 024 → generate bounded proposal
→ Entity A approves (issuer)          → telemetry still 403
→ Entity B accepts constrained lease  → telemetry 200
→ citizen records 403 RESOURCE_CLASS_DENIED (always)
→ isolate B-17 → 409 HUMAN_APPROVAL_REQUIRED
→ Entity B issues exact one-use approval → isolate 200, connector v1→v2 (once)
→ revoke lease → telemetry 403 AUTHORITY_REVOKED
```

## Stack

- Next.js 16 (App Router, Node route handlers), React 19, TypeScript, Tailwind 4
- SQLite via `node:sqlite` (server-owned state, `data/qalaa.sqlite`, override with `QALAA_DB_PATH`)
- Vitest for direct API tests

## Architecture

| Layer | Where |
|---|---|
| Domain types & seed | `src/lib/domain/` |
| SQLite store, reset, opaque demo sessions | `src/lib/db.ts`, `src/lib/store.ts` |
| Central resolver (every protected call) | `src/lib/resolver.ts` |
| Protected Entity B operations | `src/lib/protected.ts` |
| Lease lifecycle, step-up, revoke, reset | `src/lib/lifecycle.ts` |
| Bounded proposal + policy validation + rule fallback | `src/lib/proposal.ts`, `src/lib/model.ts` |
| Snapshot, demo step, authority graph | `src/lib/snapshot.ts` |
| Route handlers | `src/app/api/**` |
| Command center UI | `src/components/` |

### Trust boundary

- Identity comes from a server-issued opaque session token (`x-qalaa-demo-session`),
  minted by `POST /api/demo/session` for one of three synthetic roles. Any client-supplied
  identity, lease, approval, policy or connector state is ignored.
- Every protected endpoint calls `authorize()` in `src/lib/resolver.ts`, which checks:
  principal → resource/action binding → policy class deny → mission → lease binding →
  lease status/expiry → issuer approval → receiver acceptance → policy severity/scope →
  lease scope → exact one-use human approval (for gated actions) → pre-mutation recheck.
- Every attempt (allow, deny, step-up) persists a `DecisionRecord` and returns a
  server-generated `receiptId`.
- The connector mutation runs inside a SQLite `BEGIN IMMEDIATE` transaction with a
  recheck, so approval consumption and state change are atomic and happen once.

### Governance model (optional)

`POST /api/leases/propose` makes at most one bounded model call (8 s timeout, strict
JSON) when `QALAA_MODEL_API_KEY` (or `OPENAI_API_KEY`) is set; `QALAA_MODEL_BASE_URL`
and `QALAA_MODEL_NAME` are optional. The output is validated against Entity B policy;
over-reaching terms are recorded as rejected and excluded. On absence, timeout, or
invalid output the proposal is generated by deterministic rules and labeled
`RULE FALLBACK`. The model can only propose — activation requires Entity A approval
and Entity B acceptance, and the resolver never consults the model.

## API

Protected (Entity B), as Agent 47:

- `GET  /api/entity-b/security-telemetry`
- `GET  /api/entity-b/citizen-records` — always 403 `RESOURCE_CLASS_DENIED`
- `GET  /api/entity-b/connectors/b-17`
- `POST /api/entity-b/connectors/b-17/isolate` — 409 `HUMAN_APPROVAL_REQUIRED` without exact approval

Lifecycle:

- `POST /api/mission/declare` (Entity A commander)
- `POST /api/leases/propose` (Entity A commander)
- `POST /api/leases/issuer-approve` (Entity A commander)
- `POST /api/leases/receiver-accept` / `receiver-reject` (Entity B approver)
- `POST /api/step-up/approve` `{ pendingRequestId }` (Entity B approver)
- `POST /api/leases/revoke` (Entity B approver, or Entity A commander)

Demo:

- `POST /api/demo/session` `{ role }` → opaque token
- `POST /api/demo/reset`
- `GET  /api/demo/state`, `GET /api/demo/step`

## Non-goals

Not a chatbot, SIEM, IAM system, policy RAG, agent observability platform, or a
production federation layer.
